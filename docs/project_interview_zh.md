# 简历与面试材料

项目名称：**基于 mini-vLLM 的单机多卡大模型推理框架开发**。模型为 Qwen3-14B。实际状态、性能表和原始数据见 [L40S 实测报告](l40s_acceptance_2026-11-18_zh.md)；下面的“验证”均限定于报告中的输入、代码和配置。

## 三条简历描述

三条描述优先使用已通过限定检查的独立 TP2、双卡 PD 和 FP8 KV。四卡组合的剩余分歧在讲解中说明，不写成全部功能通过。

- 基于开源 mini-vLLM 适配 Qwen3-14B，完善 TP2 分片加载、多进程执行与 NCCL 通信，定位并修复 BF16 部分积舍入问题；在 2×L40S、4096 输入/128 输出、并发 4 的 32 请求实测中，输出吞吐 47.5 token/s、TTFT p95 为 2.50 s。
- 实现独立 Prefill/Decode worker 的 bulk KV 交接与请求状态接管，覆盖分页、首 token 归属、Decode 接管、并发及取消回收；在 Qwen3-14B 六组输入、真实双卡 1P1D 部署上验证有效 KV 字节一致及输出对齐。
- 实现 E4M3FN FP8 KV 的运行时量化、token/head FP32 scale 存储及 Triton attention 反量化读取；在相同 20,480 token 池容量下，将 KV data＋scale 从 3.125 GiB 降至 1.611 GiB，六组短生成与 BF16 KV 一致，并记录 FP32 prefill 的延迟代价。

如版面只能保留两条，合并第一、二条。吞吐与 TTFT 是同一批有限样本的绝对结果，不是最大吞吐或稳定 SLA；其余 mean、p50、p95、p99 和每卡显存留在报告里。需要提及四卡时，只能写实际运行的 TP2 P＋两个 TP1 D 原型，并说明仍有一个固定输入的输出分歧。不要写“FP8 权重量化”“无精度损失”“所有配置严格对齐”“相比 vLLM 加速”。

## 三分钟讲解

这个项目基于开源 mini-vLLM，围绕 Qwen3-14B 做 TP2、多实例 P/D 交接和 FP8 KV。模型骨架和基础 attention 来自上游，我主要改造分片加载、执行协议、KV 生命周期、P/D 状态和 FP8 存储读取，并做真实多卡验证。

TP2 中，QKV 和 gate/up 按输出切分，o_proj 和 down_proj 按输入切分并归约；rank 0 聚合 logits、采样和下发命令。我遇到过一个具体数值问题：原 tiny 的第三个输出与 TP1 不同。捕获并重放首个差异算子后，证明输入、权重分片一致，差别来自部分积先舍入 BF16 再归约。修复保留 BF16 输入和权重，只把部分积和归约保留 FP32，最终再转 BF16。原严格用例通过，14B 六组各 16 个输出也与 TP1 一致，没有放宽容差。

P/D 两端有独立 KV 块。prompt 长 N 时，P 生成首 token，但缓存只覆盖 prompt 的零到 N 减一位置；D 恢复后，在位置 N 处理首 token，再生成第二个，避免重复或漏 token。双卡 1P1D 在六组输入上验证有效 KV 字节一致，并覆盖并发与取消回收。四卡 TP2 P 加两个 TP1 D 也实际运行，但一个短输入仍有输出分歧，我把它列为组合限制。

FP8 仅压缩 KV，权重仍 BF16。每个 token/head 保存 FP8 数据和 FP32 scale，读取时反量化。head_dim 为 128 时，存储从 256 字节降到 132 字节，固定 KV 池节省约 48.4%，总显存不会减半。默认 FP32 prefill 在 4K 输入上反而很慢，所以我只主张存储收益，保留延迟代价。

最后固定 4K 输入、128 输出，测并发 1 和 4 的吞吐、TTFT/TPOT 分布与每卡显存。TP2 并发 4 的 32 请求实测为输出 47.5 token/s、TTFT p95 2.50 秒；同负载 TP1 吞吐更高，所以没有宣称 TP2 加速。我还单独采两个 TP rank 的 profile，观察到计算、NCCL 和两 rank 等待不对称。这是经过有限验证的开发原型，个人实现、上游来源、通过范围和组合限制都保留证据。

## 常见追问

**TP 和 P/D 分离分别解决什么问题？**

TP 将同一个模型的计算和部分权重分到多个 rank，一次 forward 内需要通信。P/D 将 prompt 计算和后续逐 token 生成交给不同实例，需要迁移 KV 和请求进度。二者不是同一维度，增加 GPU 数本身不保证请求更快。

**四卡怎样部署？**

实际启动一个 TP2 P 和两个 TP1 D：P 占 GPU0/1，两个 D 分别占 GPU2/3。进程、请求交接、并发和回收运行，修复后六组串行输出有 5/6 与 TP1 一致，chat-1 第 10 个输出仍分歧。因此只能说四卡部署原型实际运行，不能说四卡组合完整正确性通过。

**P 的 KV 已经分片，TP1 D 怎样恢复？**

每个 P rank 持有自己的 KV heads。bulk 导出将各 rank 数据移到主存，经独立 Gloo 组按全局 head 顺序汇总，再按 D 的本地 block table 写回。模型计算的 NCCL 组和主存汇总组承担不同职责。这里没有实现 GPUDirect、RDMA 或零复制。

**为什么只交接 prompt KV，首 token 的 KV 在哪里？**

P 用 prompt 最后位置的 logits 采样首 token，此时首 token 尚未作为模型输入，缓存里只有 prompt KV。D 在位置 N 处理首 token 时生成它的 KV，再预测第二个。首 token 已终止或只要求一个输出时不交接。

**分页边界具体检查什么？**

检查长度 N 对应的有效块数与尾块有效 token 数，不能把整个预分配池当成有效 KV。255/256/257 分别覆盖不足一页、整页和跨页；4096 覆盖多页。源块编号不需要等于 D 的块编号，顺序、有效位置和请求映射需要正确。

**FP8 的量化过程是什么？**

K/V 分别对每个 token/head 求绝对值最大值，用 `scale=max(amax/448,float32_tiny)`，全零 head 用 1；除以 scale、裁剪后写入 E4M3FN。scale 使用 FP32。KV data 为 `[2,layers,blocks,block_size,local_kv_heads,head_dim]`，scale 去掉最后一维。PD 传原始 data＋scale，不再次量化。

**为什么 KV 存储减半左右，显存没有减半？**

权重仍占约 29.54 GB，此外还有 RoPE、activation、CUDA/NCCL 和 allocator 保留空间。这里只改变 KV data，并增加 scale。固定池的字节数、当前有效 token 数和设备总显存是三个不同口径。

**为什么 FP8 反而慢？**

当前实现是压缩存储与读取时反量化，并没有调用 FP8 GEMM；默认 prefill 中间计算使用 FP32。实测只证明这条路径在固定负载上的时间，不能因为硬件支持 FP8 就推断会加速。后续可以研究计算 dtype 和 kernel，但不属于这轮已完成的优化。

**TP2 输出为什么会不同？是否就是实现错误？**

修复前 tiny 的第三个输出和 14B 一个短输入的第十个输出分歧，都对应 TP1 top1/top2 并列。不能仅凭这一点豁免失败；本轮额外核对权重/输入分片，并精确重放全部 113 个首边界差异，才选择 FP32 部分积与归约。原严格用例和独立 14B TP2 的六组输出现在通过，但四卡 TP2＋PD 仍有分歧，且不声称所有 logits 或所有输入等价。

**少量 token 一致能说明精度无损吗？**

不能。固定样本能发现路径、位置、严重数值和传输问题，但不能替代任务质量评测，也不能保证更长输出、其他提示或其他 kernel 配置。logits 误差、同前缀 top1 和独立生成分别记录。

**性能数据能说明什么？**

说明固定模型、输入、输出、采样、缓存和设备配置下的小批次行为。TP1/TP2 并发 4 各补了 32 请求，其他路径每档 8 请求。TTFT/TPOT 同时报告 mean、p50、p95、p99，但这些仍是经验分位数，没有稳定尾延迟或最大容量结论；不同卡数不直接计算同资源加速比。修复后独立 TP2 与存在分歧的四卡组合分别列出，后者计时只作诊断。

**为什么没有直接装一整套 vLLM benchmark？**

服务端已经提供 OpenAI 兼容流式接口，可以直接被官方 `vllm bench serve` 测量。租机复用已有轻量环境，正式请求原样使用 vLLM 0.15.0 的 HTTP 请求函数，外层只管理并发、固定输入和结果保存；分位数和吞吐另用本地原版 `calculate_metrics` 对全部保存批次复算一致。因此无需为了测量重新安装服务端依赖。官方 CLI 替代命令保留在报告，不能声称本轮跑的是赛事专用脚本。

**total tokens/s 和 output tokens/s 有什么区别？**

前者用成功输入＋输出 token 总数除以批次墙钟，后者只用输出 token；这里输入/输出固定为 4096/128，所以总吞吐恰好是输出吞吐的 33 倍。它们强调的工作量不同，必须连同长度、并发、卡数和测量范围一起解释，不能拿不同长度的总吞吐直接比较。

**哪些是个人贡献，哪些来自上游？**

上游提供模型骨架、TP 层、调度器、基础 Flash/Paged Attention 和 CUDA Graph。项目改造包括严格加载与覆盖检查、执行和回收适配、数值修复、P/D 协议及 KV 恢复、FP8 KV 与验证工具。性能 HTTP 请求函数原样复用 vLLM 0.15.0 并保留版权和许可证，不算原创。代码入口和历史差异见实测报告及各阶段说明。
