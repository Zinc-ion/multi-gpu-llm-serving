# Qwen3-14B 三卡推理优化阶段报告

截至 2026-11-24（新加坡时间）。测试分支 `test/fp8-layer-rpc-timing`，四帧实现 `95be995`，窗口兼容性与容量报告 `fd2fdd9`。

## 做了什么、为什么做、收益如何

- **共置分块 prefill**。把长 prompt 拆为每步最多 1024 token，给正在解码的请求留下调度机会。与整段共置相比，有中段停顿超过 500 ms 的请求从 16/32 降到 2/32，输出吞吐从 97.33 变为 96.78 tok/s，TTFT P95 从 0.88 增至 1.38 s。
- **P/D 分离与逐层发送**。整包发送会把 KV 交接暴露在首、次 token 之间。按层就绪即发，使传输可以与后续层计算重叠。BF16 下首二间隔 P95 从 11.00 降到 1.97 s，输出吞吐从 78.54 增到 91.54 tok/s；TTFT P95 从 3.03 增到 3.86 s。后端对照中，本机 socket 优于此次 Mooncake TCP 接入。
- **FP8 KV 与 query 精度的 prefill attention**。FP8 KV 将每请求交接量从 640 降至 330 MiB（含 10 MiB scale）；模型权重和激活保持 BF16。将反量化后的 K/V 转回 Q 的 BF16 精度，避免该路径使用 FP32 点积。FP8 整包的 TTFT P50 从 34.84 降到 0.90 s，吞吐从 41.32 增至 88.27 tok/s。再叠加逐层发送，首二间隔 P95 从 5.87 降到 0.93 s，吞吐达到 95.27 tok/s，比 FP8 整包高 7.9%。
- **网关有界 FIFO**。4 个活跃位满时允许另 4 个请求等待，限制等待时长。集成复测 32/32 成功，达到 95.07 tok/s；这次客户端并发上限就是 4，实际入口排队为 0，因此该吞吐只能验证组合运行。另行固定到达时间线的配比回放见已有三卡报告。
- **分块计算与尽早释放 KV**。4K prompt 拆为 4 步，先用“末步发整层”的 40 帧配置观察分块计算，再把 KV 切成 160 帧，固定帧数对比末步发送和尽早发送。窗口 1 时，尽早发送的 TTFT P95 从 11.05 降至 9.78 s，吞吐从 82.92 增至 84.42 tok/s。末步发整层的 40 帧配置仍有 93.80 tok/s；更细的帧让传输更早具备发送条件，也带来了更多接收端提交。
- **D 端四帧连续提交**。P 端允许多帧在途，D 端按四帧向执行线程提交一次，保持帧顺序并逐帧 ACK。忙解码微实验中，首帧发送到末 ACK 平均耗时依次为原窗口 6.295 s、仅增加槽位 6.267 s、仅放宽发送而保留逐帧提交 6.248 s、四帧分组提交 1.784 s。对应 D 端排队时间从 5.093 降至 0.855 s，说明减少与解码争用执行线程的提交次数，是此微实验中的主要收益。正式批次中，末步发送的传输均值从 5.762 降到 1.644 s，尽早发送从 5.390 降到 2.730 s。窗口 4 为可选模式，默认窗口为 1。

## 对比总表

## ⚠ 尽早发送四帧的吞吐回落，待空闲同场复测

84.42 → 52.76 tok/s（−37.5%）是两轮历史实测。相同输出量的批次耗时从 388.18 增至 621.06 s。排除与任一 P 端 prefill 步骤或 KV 传输重叠的客户端解码间隔后，均值从 39.40 增至 71.44 ms，P95 从 40.29 增至 130.26 ms。把样本进一步限于同一 D 上恰有两个请求处于持续输出阶段，中位间隔仍从 39.45 增至 62.02 ms。现有证据把主要延迟定位到后续解码阶段，无法单独确定 CPU 调度、其他主机争用或窗口实现各自的贡献。

历史四帧正式批次全程与同机 CPU 回归测试重叠。后来准备交替复测时也观测到外部 CPU 负载；后一次账号采样不能追溯归因到历史批次。此次中止的单帧轮已通过逐 token 校验和预热，正式批次未完成，未计入表格。同场待测顺序为窗口 1、4、1、4，固定尽早发送、三卡、清单及并发，逐轮记录主机负载、D 端线程调度等待和 GPU 时钟。
