# 单机多卡推理框架：最小验收与交付

配合 [任务](m8.md)、[需求](../../docs/llm_serving_project_requirements_zh.md) 和 [支持矩阵](../../docs/inference_optimization_overview_zh.md) 使用。目标为 Qwen3-14B；每项通过只对应所列代码、模型、硬件、精度和配置，不表示生产可用或完整性能研究完成。旧任务要求由本清单覆盖。

## 1. 基本路径

| 路径 | 验收内容 | 最小资源与边界 |
|---|---|---|
| BF16 TP1 | 目标模型加载、固定代表输入，greedy 与必要同前缀 logits 对可信参考 | 一卡；旧 M2 数据只作为历史参考，最终版本需复验 |
| BF16 TP2 | 加载覆盖、分片、进程/rank 与通信；固定输入对可信 TP1 | 两卡；误差、容差依据、首分歧与定位记录齐全，不放宽门槛掩盖问题 |
| BF16 bulk PD | 独立 P/D、KV 导出/恢复和请求状态交接 | 优先双卡 TP1＋TP1；不以四卡或 TP2＋PD 为前置 |
| FP8 KV TP1 | 权重/scale/布局/kernel 审计、运行时量化/读取与少量结果检查 | 一卡；当前权重/activation 为 BF16，没有 FP8 权重或 GEMM |
| 组合支持 | TP2＋PD、FP8＋TP2、FP8＋PD 等逐项记录 | 不要求全部补齐；四卡声明须有真实四卡结果 |

矩阵使用“已实现且验证通过”“已实现但待验证”“存在已知问题”“尚未支持”，写明 tiny、旧模型、旧机器与当前 Qwen3-14B 的边界。若某项需结构性重做，说明工作量与未完成范围，先交付其余成立项，不能用缩小范围将失败记为通过。

## 2. 正确性和交接

- 原 tiny TP2 BF16 `[32,33,62]` 对 HF/TP1 `[32,33,41]` 是修复前失败；2026-11-18 以 Row 部分积精度修复后原 GPU FP32/BF16 两项通过，14B 六组 greedy 与同前缀 top1 一致，见 [实测报告](../../docs/l40s_acceptance_2026-11-18_zh.md)。保留原输入、seed、dtype、容差与失败记录，不能将旧 tiny 容差当作 14B 门槛，或将少量输出一致称为所有 logits 等价。
- 目标模型 BF16 TP2 对可信 TP1，用相同输入和采样，记录最大/平均 logits 误差、同前缀 top1、首个 token 分歧及 top1/top2 margin。不能用换 seed 或不断放宽容差掩盖异常。可信框架只需用于必要正确性参考。
- PD 覆盖有效 KV 长度、分页边界/尾块、请求映射、独立 D block table、接管位置、少量并发交错、EOS/输出上限、完成与取消回收。P 生成首 token；prompt 长 N 时交接 `[0,N)`，D 在位置 N 处理首 token 并生成第二个；首 token 即结束时不做交接。无重复/遗漏 token，不用 D 重算 prompt 冒充恢复。
- 同格式 P→D 比较有效 KV；FP8 同时核对原始 data 和 scale 字节，尾块按有效/填充契约处理。若验证 TP2 P bulk，另核对全局 KV head 汇总顺序；TP>1 D、TP2 pipeline 当前入口拒绝，不写成支持。
- FP8 审计明确权重格式、量化发生位置、scale 粒度、缓存布局和实际计算内核，区分接入预量化权重、复用算子与自己实现的量化过程。当前实际实现为 FP8 KV，按该范围命名。
- 少量固定代表输入比较 BF16→FP8 的 finite、logits 和输出，注明长度、生成预算与计算模式。有损量化差异与同格式交接误差分开；不要求两种 KV 格式 token 完全相同，也不声称“无精度损失”。
- 正常、少量并发和取消后，检查请求/KV/传输预留回收，后续请求能完成；不增加生产故障全矩阵。已有逐层路径仅在容易验证时补记，不新开深化任务。

## 3. 小规模测量与 profile

优先比较通过对应正确性检查、实际能运行的 BF16 TP1、BF16 TP2、FP8 KV TP1、BF16 PD。固定约 4096 输入/128 输出、并发 1 和一个可运行点；按实际资源调整并保存原因，不展开扫描。不同卡数和部署方式逐行标注，不包装成同资源加速比。

各路径尽量共用模型/tokenizer、实际 token 输入、输出预算、greedy/ignore-eos 和缓存设置；FP8 KV 为明确变量，其他运行差异注明。有限预热与正式批次分开，数值捕获和 profiler 关闭后测性能。

每行必记：

- 请求数、成功数、失败数及原因，预热数量、实际输入/输出 token、并发、GPU 数和部署方式。
- TTFT、逐请求 TPOT 的 mean、p50、p95、p99；说明成功且可计时样本数量与分位数插值方法。单 token TPOT 为不适用，不把 chunk ITL 当成逐 token 间隔。优先从已有逐请求数据补统计，最终有效配置适当增加样本，不另建大型测试工程。
- 成功请求输出 token 总数/正式墙钟时长；成功请求输入＋输出 token 总数/相同墙钟时长。说明批次起止、完成尾巴，排除预热。
- 权重字节、KV data＋scale/实际池、总运行显存；注明 PyTorch allocated/reserved/peak 或 nvidia-smi 设备采样与间隔，多进程/卡的汇总方法。预分配容量不等于实际用量，KV 节省不等于总显存减半或加速。
- PD 必要时记客户端首二 token 间隔和内部 export/restore/handoff 口径；跨进程绝对时钟不直接相减。
- 原始逐请求结果、输入、配置、命令和环境。短样本不写成稳定尾延迟、最大 goodput 或普适收益。

另采一段代表性短 profile，保留 trace、命令、配置及时间区间，说明计算、通信/复制与等待的大致分布和进程覆盖。没有 TP/PD 通信则注明，不叠加重叠时间制造百分比。profile 与正式性能数据分开，不要求逐层优化、正收益或战胜 vLLM。

## 4. 成本与收尾

沿用已提供机器与环境，不额外租机、改变计费或擅自开启 GPU。无卡准备完成并需要真实验收时通知用户开启 4×L40S，开卡后核对实际设备/拓扑和资源预算；旧 GPU0/1/3/4、NUMA 假设不直接套用。学校内网服务器的新增文件限制仍为 `/Data2/zincion/ai-infra`；当前 L40S 租机的任务文件、环境、模型、缓存及日志使用数据盘目录 `/root/data/zincion/ai-infra/l40s-20261117`，见 [租机记录](../../docs/server_hardware_l40s_2026-11-17.md)。

中间改动运行相关测试，最终集成一次完整 CPU 回归及相关 GPU 验证。CPU/Gloo、同卡 tiny GPU、旧模型和旧环境结果分别记录；未运行、skip 和失败如实保留。无需新实验控制器、反复 SHA/快照/标签或额外审批文件。

最终交付：可运行代码与必要修复/命令、支持矩阵与限制、正确性/原始端到端数据/短 profile、架构与贡献报告、三条可复制简历描述、三分钟讲解和常见问答。数字只取实测，可写绝对性能和资源；未验证功能、未解问题和旧模型结果不能包装成 Qwen3-14B 已完成成果。
